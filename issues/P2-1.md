# P2-1 — The write-then-emit pattern leaves a window where the write succeeds …

## Finding / 问题

- EN: The write-then-emit pattern leaves a window where the write succeeds but the side effects fail, leaving the caller with a success return and inconsistent state. This is a documented design trade-off — idempotent consumers are the prescribed answer — but it is still a robustness gap.
- 中文: 先写后 emit 模式留下一个时间窗口：写入成功但副作用失败，调用者拿到成功返回值而状态不一致。这是文档化的设计取舍——规定消费者要保证幂等——但它仍然是一个健壮性缺口。
- Where / 位置: `src/BaseManager.php:48-56, src/EventBus.php:129-140`
- Verification / 验证: static / 仅静态推断

- 2026-09-29 · `owner — migears-manager` · `question` — reproduced, and the remedy forks on a behaviour decision
  that is yours, not mine.

  **Reproduced** (probe outside the repo, loading this module's own `vendor/autoload.php`). One listener on
  `order.placed` reads the row, finds it already persisted (`PLACED`), then throws. The probe printed
  `SideEffectFailedException(event=order.placed, previous=listener boom)`; the row stayed persisted; the entry
  layer's retry wrote a second row (`getByIdOrFail(2)` succeeded). The finding's consequence is real, and
  `tests/BaseManagerTest.php:164` already pins it: mutating `src/BaseManager.php:98-105` to swallow the listener
  failure (instead of wrapping it) makes that test fail at `tests/BaseManagerTest.php:179` — so the current
  behaviour is genuinely load-bearing, not incidental.

  **Why `question`, not `fixed`.** There is no local patch. The window is the direct consequence of two decisions
  this package documents and deliberately keeps: synchronous in-stack delivery (`src/EventBus.php:127`,
  `README.md:634-641`) and no transaction manager / no "after commit" dispatch (`README.md:643-655`,
  `README.md:977`). Every honest remedy changes behaviour, so the choice is yours.

  **The fork, and what each option costs:**
  1. **Keep it (no change).** Documented at `README.md:643-655` and pinned by `tests/BaseManagerTest.php:164`;
     consumers answer with idempotency. Cost: the window stays, so a non-idempotent retry duplicates the write.
     Adds no public surface; breaks nothing. Owner's recommendation.
  2. **Deferred / "after commit" dispatch.** Cost: a new public concept and API (what flushes the queue, and
     when?), a change to synchronous delivery (`README.md:634-641` point 1), and a direct contradiction of
     `README.md:977` ("No deferred or 'after commit' dispatch"). Behaviour + breaking change.
  3. **A transaction seam** — the Manager receives a `PDO` and wraps write+emit in one DB transaction. Cost:
     `README.md:567` already allows a `PDO` parameter for exactly one transaction, but `emit()` sits inside the
     Manager while the DAO owns its connection (`README.md:336-339, 464-467`), so this needs DAO cooperation or a
     connection held below the Manager; it also cannot cover non-DB side effects, so the window stays for those.
     Behaviour change plus new coupling below the Manager.

  No source or test file was changed: the mutation was reverted, and `git status` shows only this item file
  (`issues/P2-1.md`) modified against `HEAD` = `608d225`.

**分叉点，以及各选项的代价：**
